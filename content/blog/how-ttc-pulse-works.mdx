## Problem

The TTC publishes delay logs for bus, subway and streetcar. Route labels in the logs are free text. They do not join to the TTC schedule as they are. TTC Pulse cleans these files, joins them to the GTFS schedule, and ranks each route and station with one reliability score.

## Data

TTC Pulse uses three sources:

- **Delay logs.** TTC Bus, Subway and Streetcar Delay Data from City of Toronto Open Data (Open Government Licence, Toronto). The data has 1,111,831 delay events from 1 January 2014 to 31 January 2026: bus 723,518, subway 235,397, streetcar 152,916.
- **GTFS schedule.** The TTC routes, stops and services. The route dimension has 229 routes (`dimensions/dim_route_gtfs.parquet`).
- **GTFS-Realtime alerts.** One alert build on 16 April 2026 gave 37 alerts and 5,984 entity rows. 99.5% of the entity rows match a GTFS route.

The delay logs record delay events only. They do not record the trips that ran on time. Thus every count in TTC Pulse is a count, not a rate.

## Architecture

```pipeline

```

- **Bronze** keeps each source row as it arrived. Each row has `source_file`, `source_row_id` and `row_hash` (`src/ttc_pulse/bronze/build_bronze_tables.py`). All 1,111,831 delay events keep these fields, so each one traces back to its file and row.
- **Silver** normalizes dates, routes, stations and causes into one fact table (`silver/fact_delay_events_norm.parquet`).
- **Gold** has 8 marts in 22.0 MB of Parquet. The largest are `gold_delay_events_core` (1,086,378 rows), `gold_route_time_metrics` (893,537 rows) and `gold_station_time_metrics` (223,480 rows).
- **Export.** A script in the TTC Pulse repo (`scripts/export_site_data.py`) reads the gold marts and writes small JSON files.
- **Site build.** The site runs Next.js 15 on Cloudflare Workers through OpenNext. The dashboard imports the JSON files at build time. The page does not query a database.

## Method

### Route matching

The bus normalizer puts each route label into one of three tiers (`src/ttc_pulse/normalization/normalize_bus.py:94-104`):

1. **Exact.** The full label is a route number, for example `32`. Confidence 1.0.
2. **Token.** The label starts with a route number, or contains `LINE n`. Confidence 0.95 to 0.70.
3. **Fallback.** The label has no route number. Confidence 0.0.

Then the normalizer joins the route number to the GTFS route list. A route number with no GTFS route gets `link_status = unmatched_review` and a confidence of 0.35 or less (`normalize_bus.py:159-174`).

Across all modes, 95.8% of delay events (1,065,527) match by the exact tier and 4.2% (46,304) by the token tier. The committed fact table has no fallback rows. For bus, 97.7% of delay events (706,725 of 723,518) match a GTFS route. The other 16,793 (2.3%) are `unmatched_review`.

### Reliability score

I wrote the first version of the score in `src/ttc_pulse/marts/scoring.py:14-17` and `:74-79`:

```
score = 0.35 z(frequency) + 0.30 z(severity_p90) + 0.20 z(regularity_p90) + 0.15 cause_mix
```

- **Frequency** is the number of delay events.
- **Severity** is the 90th percentile of delay minutes (`build_gold_route_metrics.py:65-67`).
- **Regularity** is the 90th percentile of gap minutes between vehicles.
- **Cause mix** is 1 minus the sum of squared cause shares (`build_gold_route_metrics.py:88`). This is a diversity index, not a z-score (`scoring.py:72`).

In the route mart, each z-score compares a route with the other routes of the same mode, service date and hour (`build_gold_route_metrics.py:26`). In the ranking mart, each z-score compares an entity inside one ranking date, mode and entity type (`build_gold_rankings.py:32`). The ranking window is the 90 days to 31 January 2026 (`build_gold_rankings.py:77`).

`scripts/check_readme_numbers.py` recomputes the stored score from its four inputs for all 893,537 route rows. The largest difference is 2.2e-16.

## A check on the score

The score has a small-sample fault. In `gold_top_offender_ranking` for bus routes, route 28 Bayview South ranks 1st with 10 delay events. Route 32 Eglinton West has the most delay events (447) and ranks 9th.


8 of the top 10 have fewer than 60 delay events. Their `severity_p90` is 287 to 471 minutes. With few delay events, one long delay sets the 90th percentile. The pipeline sets bus delays of 999 minutes or more to null (`_gold_utils.py:214`), but values below 999 stay.

On the site I added an adjusted score as a prototype method:

```
adjusted = score × n / (n + k)
```

Here `n` is the number of delay events of the entity in the 90-day window. `k` is the median `n` for that mode and entity type (bus: 54). This is a simple credibility weight. It pulls a score with a small `n` toward the mean, which is 0 for a z-score. The limit: `k` is a rule of thumb. I did not fit it to the data.

## One query and its result

This query computes the adjusted score from the ranking mart and adds the route names:

```sql
WITH r AS (
  SELECT entity_id, frequency AS n, severity_p90, composite_score, rank_position
  FROM read_parquet('gold/gold_top_offender_ranking.parquet')
  WHERE mode = 'bus' AND entity_type = 'route'
),
k AS (SELECT median(n) AS k FROM r)
SELECT r.entity_id, d.route_long_name, r.n, r.severity_p90,
       round(r.composite_score, 2) AS score, r.rank_position AS raw_rank,
       round(r.composite_score * r.n / (r.n + k.k), 2) AS adjusted,
       rank() OVER (ORDER BY r.composite_score * r.n / (r.n + k.k) DESC) AS adj_rank
FROM r, k
LEFT JOIN read_parquet('dimensions/dim_route_gtfs.parquet') d
  ON d.route_id = r.entity_id
ORDER BY adjusted DESC
LIMIT 5;
```

Result (TTC Pulse commit `d5d2a02`):

## Options and decision

The team built the first dashboard in Streamlit (`app/pages/`). For a public link, I compared two ways to serve it.

| | Streamlit server on AWS | Static rebuild on the site |
|---|---|---|
| Monthly cost | A server that runs all the time | $0 on the existing Cloudflare site |
| Link works when | The server is up | The site is up |
| Data freshness | Can query the marts live | Fixed at the last export |
| Interactive filters | All Streamlit pages | Only the views I rebuilt |
| Work to keep | Server, updates, access | One export script and one build |

**Decision:** a static rebuild on the existing Cloudflare site. The cost is $0 a month. The recruiter link never depends on a server. The cost of this decision is freshness, but the gold marts stop at 31 January 2026, so a live query adds no new data.

## Failure modes

- **The export is stale.** The page loads and shows the numbers from the last export. To fix it, run `scripts/export_site_data.py` again and rebuild the site.
- **A route does not match GTFS.** The delay event gets `unmatched_review` and no `route_id_gtfs`. Route marts do not include it: `gold_route_time_metrics` has 0 rows with a NULL route. The 16,793 unmatched bus delay events stay in silver for review.
- **The alert parser runs twice.** The parser is not idempotent. A second run appends the same alert rows again, so alert counts increase. A fix is a unique key on snapshot time, alert and entity.
- **The site build fails.** If `npm run cf:build` fails, `cf:deploy` does not run. Cloudflare keeps the last deployed version live.

## Limits and what I would change

- The raw files and the DuckDB database are not committed. The full pipeline does not run from a clone. The committed Parquet layers can be queried from a clone.
- 60 of 234 snapshot files do not match their recorded checksum.
- The repo has no tests and no CI. I would add `check_readme_numbers.py` to CI first, because it already exits 0 on a correct build.
- I have not run the `aws/` kit (S3, Glue, Athena) yet.
- Newer cause rows use raw codes, for example `MFWEA`, that have no description in `dim_incident_code`.
- Yonge Station has 2,343 of its 8,229 delay events at 22:00, with the top cause "Miscellaneous Other". This needs a check before anyone uses the station ranking.
- To turn counts into rates, I would join the GTFS trip counts per route and hour.
- I would fit `k` in the adjusted score from the data, and not use the median.
